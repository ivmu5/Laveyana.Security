# Laveyana.Security — experimental adoption and known limitations

**English** | [Русский](Laveyana.Security.KnownLimitations.ru.md)

**Status date:** 21 October 2026  
**Release state:** pre-release (`1.2610.0-alpha.1`); **Phase 27 production security gate: NO-GO**.

This is the current, concise adoption policy for trying the library **before** all security acceptance gates are closed. It records what can reasonably be piloted and what is *not* guaranteed. It does **not** declare the library secure for production secrets, certify a deployment, or replace the detailed [Phase 27 audit](Laveyana.Security.Phase27.SecurityAudit.md). Results from a supplied source ZIP must not be silently attributed to a different Git commit.

## Permitted pilot scope

| Area | Current recommendation |
| --- | --- |
| In-memory primitives, contracts and provider composition | Suitable for **development, tests and controlled internal evaluation**, with application-specific cryptographic design and error handling. A passing library test suite is not proof that the application's protocol is safe. |
| Software-managed ephemeral key operations | Evaluate with disposable data and explicit key/material ownership. Enforce the per-instance AEAD nonce restrictions described below. |
| `Laveyana.Security.FileSystem` | **EXPERIMENTAL / TEST ONLY.** Ordinary writes require explicit `EnableExperimentalWrites`; use isolated, disposable test storage, not production secrets or sole copies of valuable keys. |
| Windows DPAPI CurrentUser protector | Windows/user-profile-bound component only; selecting DPAPI does **not** make the experimental filesystem store production-approved. |
| Rollback-sensitive persistence, protected filesystem writes and production key custody | **Not approved.** Choose an independently reviewed storage/provider solution if the application already requires these properties. |

## Open findings and relevant limitations

| ID / area | Current state | Boundary that matters to adopters |
| --- | --- | --- |
| **SA-03 — snapshot rollback / replay** | **OPEN** | Snapshot integrity/authentication cannot detect a replayed, previously valid state. Optional external rollback-authority contracts and read-only inspection exist, but a complete durable protected writer/recovery protocol, downgrade prevention and a built-in independent authority do not. `ProvidesRollbackProtection=false`. |
| **SA-04 — AEAD nonce lifetime** | **OPEN** | Randomized software AES-GCM encryption is supported only for material freshly generated by the **same** `SoftwareKeyProviderBackend` instance, up to `2^20` issued nonces for that material. Restart, import, reopen, restore or memory cloning does not establish a new safe encryption lifetime; rotate to newly generated material. Decryption of historical ciphertext is distinct. The bundled backend rejects deterministic nonce allocators. |
| **SA-08 — storage durability / adversarial acceptance** | **OPEN** | Process termination and fault-injection coverage are **not** a real power-cut test. Linux `fsync(file)` and `fsync(directory)` were exercised on a container overlay filesystem, not qualified for an actual disk/storage chain. Windows has no demonstrated post-rename directory-namespace durability barrier. VM hard power-off and physical power-loss tests were **not run**. |
| **SA-02 — path substitution / TOCTOU** | **CLOSED, scoped** | Handle-relative operations and related Windows/Linux regression cases support a limited engineering closure. This is not a guarantee against every race, deployment/ACL misconfiguration or filesystem behavior. It does not close SA-08. |
| **Best-effort observability / audit delivery** | **Limited, non-transactional** | The optional audit sink is dispatched asynchronously with a bounded in-flight budget. Events may be dropped, arrive out of order or be lost on shutdown. Do not use it as a compliance-grade durable audit log. |
| **Lifecycle and failure handling** | **Caller responsibility** | Cancellation after possible publication is not guaranteed rollback. Treat uncertain commit outcomes as requiring inspection/reconciliation, **not** automatic retry. External backup/restore and independent host coordination remain application responsibilities. |
| **Feature surface** | **Not implemented** | Public HPKE `Seal/Open`, encrypted streaming AEAD, durable general-purpose asymmetric private-key execution and a built-in persistent generic-secret backend are unavailable. |
| **Distribution** | **Pre-release** | Assemblies target `net10.0`; `IsPackable=false`; no public NuGet package or API stability promise is implied. Use explicit project references for pilots and pin the exact revision. |

## Evidence and its limits

- **H01 (16 October):** required Windows/Ubuntu Release CI and a manual multi-run regression completed successfully. This established development infrastructure, **not** security certification.
- **SA-08 (21 October), Linux execution review:** a separately supplied source export built cleanly and ran **334 passing unit tests** and **126 passing integration tests**; **41 additional integration results were `NotExecuted`**, predominantly Windows-specific. Selected process-kill and injected-error probes passed on Ubuntu container overlayfs. The review did **not** run Windows tests, controlled hard power-off or physical power loss on that exact export.
- A separate SA-08 execution report could not run .NET and used only Python/native probes. These reports have different execution capabilities and must not be combined into a claim of complete cross-platform durability evidence.
- No verified reproducer of new snapshot corruption was produced by those Linux probes. **Absence of a reproducer is not evidence of absence of vulnerabilities.**

## Minimum conditions when adopting now

1. Start in an internal/test application with **non-critical or reproducible data**, ideally using in-memory or disposable key material. Do not migrate irreplaceable secrets into the experimental store.
2. Fix the dependency revision; explicitly configure the chosen provider, protector and store. Do not assume `AddSecurityDefaults` provisions protected persistence.
3. Check the actual chosen API's key ownership, nonce limits, authorization, cancellation and error semantics. Wipe caller-owned secrets where appropriate.
4. Keep the existing fast Pull Request CI checks; there is **no requirement to repeat the extended regression suite solely to start a pilot**. Validate new integration behavior as it is added.
5. Reassess the unresolved findings and collect deployment-specific evidence **before** moving real secrets or production workloads to filesystem persistence.

**Decision:** **PILOT / INTERNAL EVALUATION — YES, within the limits above. PRODUCTION SECURITY ACCEPTANCE — NO.** SA-03, SA-04 and SA-08 remain open; Phase 27 stays NO-GO until separately reviewed and accepted.
