# SA-03 — контракт authority и границы интеграции

[English](Laveyana.Security.RollbackAuthorityContract.md) | **Русский**

**Текущий статус (21 октября 2026 года): только read-only inspection, локальный staging и диагностические основы восстановления; защищённые записи и автоматическое восстановление ЗАПРЕЩЕНЫ. SA-03 OPEN; Phase 27 NO-GO; FileSystem EXPERIMENTAL / TEST ONLY. Исторические разделы ниже относятся к своим контрольным точкам.**

## Угроза и граница решения

Ранее сохранённый корректный и аутентифицированный `store.lsfs` можно подставить вместо нового без нарушения проверки криптографической целостности. Ревизия конкретного ключа `KeyStoreRevision` не защищает от возврата удалённых записей, истории идентификаторов и общего состояния хранилища. Нужен **отпечаток всего снимка**, привязанный к **общей монотонной последовательности хранилища**, зафиксированный вне области, которую атакующий может откатить вместе с файлом.

На этапе 1 добавлены контракты и чистая проверка `Laveyana.Security.Abstractions.Rollback`, а также NUnit-тесты. **Не изменены** файловая реализация, формат данных, `IKeyStore`, nonce-аллокатор и объявленные гарантии. Рабочего защищённого внешнего authority пока нет.

## Новые элементы

- `RollbackCheckpoint`: закреплённый UUID `StoreInstanceId`, положительная глобальная `Sequence`, неизменяемый SHA-256-отпечаток (32 байта); передаваемые массивы копируются.
- `RollbackSnapshotDigest`: SHA-256 от домена `Laveyana.Security.RollbackSnapshot.SHA256.v1`, канонического UUID и точных байтов файла. **Хеш не подтверждает подлинность файла**: необходимо отдельно аутентифицировать содержимое и проверить закреплённый UUID.
- `RollbackAuthorityState`: последний подтверждённый checkpoint и, возможно, подготовленный **следующий** checkpoint. Незавершённая операция запрещает обычное чтение.
- `IKeyStoreRollbackAuthority`: чтение, однократная доверенная регистрация, атомарная CAS-подготовка и CAS-подтверждение. Реализация обязана обеспечивать долговечность, защиту от отката и линейризуемость между процессами.
- `RollbackSnapshotGate.Inspect`: `CommittedMatch` только при совпадении с подтверждённым отпечатком **и отсутствии pending**. `RequiresFinalization` — сигнал для отдельного восстановления, **не разрешение читать данные**. Отсутствующее authority, старый снимок и неопределённость приводят к `Rejected`.

## Этап 2A — идентификатор запроса и потерянный ответ (ТОЛЬКО КОНТРАКТ)

Исходный `IKeyStoreRollbackAuthority` сохраняет совместимость. Дополнительный
`IKeyStoreRollbackRequestAuthority` наследует его и добавляет варианты методов
регистрации, подготовки и подтверждения **с идентификатором запроса**, а также
`ResolveAsync(UUID хранилища, ID запроса)`.

`RollbackRequestId` — неизменяемый непустой GUID. Для нового действия клиент создаёт
новый случайный ID и **долговечно сохраняет его, вид операции, точные checkpoint и
кандидат для восстановления до первой возможной отправки**. При повторной передаче
используются тот же ID и те же аргументы. Authority навсегда связывает ID с одним
набором параметров и одним решением. Повторное использование ID с иными параметрами
отклоняется без изменения состояния.

Исходы `RollbackRequestResolution`:

| Исход | Смысл и поведение клиента |
| --- | --- |
| `Applied` | Именно этот запрос долговечно исполнен, даже если последующее состояние изменилось. Восстанавливать тот же переход, не повторять семантическую операцию с новым ID. |
| `NotApplied` | Запрос **гарантированно не исполнен и навсегда заблокирован** от отложенного поступления/повторной передачи. Только после этого можно рассматривать очистку связанного intent при выполнении остальных предусловий. |
| `Unresolved` | Запрос ещё может исполниться. Сохранить intent и кандидата; **отказать в обслуживании**. Простое чтение старого committed checkpoint не устанавливает окончательный исход. |

`ResolveAsync` **не имеет права** возвращать `NotApplied` лишь потому, что запрос
не найден. Сначала authority должен долговечно зафиксировать независимый запрет
(tombstone/fence) для данного ID. Если это невозможно — вернуть `Unresolved` или
ошибку. Решения и запреты должны переживать сбои, восстановление сервера из копии,
перезапуски и сетевые повторы в установленной модели угроз; удаление по TTL без
отдельного доказательства безопасности недопустимо. `false` у метода с request ID
означает долговечный окончательный отказ без эффекта данного запроса. После
тайм-аута/ошибки такой исход нельзя предполагать — нужен `ResolveAsync`. Чужой
UUID — ошибка, а не доказательство отсутствия эффекта.

**Граница безопасности:** защищённый профиль должен использовать только новые
методы с идентификатором. Реализация authority обязана исключить обход через
унаследованные методы без ID (для защищённых хранилищ они должны быть запрещены
или эквивалентно защищены). Сам интерфейс не подтверждает долговечность или
независимость стороннего сервиса — это требуется проверять отдельно.

**Не реализовано на этапе 2A:** сервер, HTTP, БД, staging на диске, протокол
commit/recovery, интеграция в FileSystem, provisioning, подтверждённая устойчивость
к отключению питания, nonce и `ProvidesRollbackProtection=true`. Тестовая
реализация хранит всё в памяти и демонстрирует только семантику.

## Планируемый порядок интеграции (ЕЩЁ НЕ РЕАЛИЗОВАН)

1. Закрепить UUID хранилища в доверенной конфигурации; аутентифицировать текущий снимок.
2. Прочитать независимое состояние authority; требовать совпадения с confirmed checkpoint без pending. Если запись отсутствует — **отказать**, не регистрировать существующее хранилище автоматически.
3. Сформировать байты следующего снимка и долговечно сохранить точные байты кандидата, ID запроса и его аргументы **до обращения к authority**; затем атомарно и долговечно зафиксировать намерение `(sequence + 1, digest)`. Тайм-аут, отмена и исключение могут означать **неопределённый результат**, а не отмену записи. Результат разрешается по точному ID; обычное чтение состояния не блокирует задержанный RPC.
4. Удерживая эксклюзивную межпроцессную блокировку, заменить файл точными байтами, к которым привязан отпечаток, и подтвердить долговечность записи. Гарантии flush/power-loss требуют отдельного аудита.
5. Долговечно подтвердить подготовленный checkpoint через CAS; перечитать и сверить authority и фактический файл до выдачи результата. Неопределённое подтверждение сверяется с authority.
6. При аварии и оставшемся pending обычное чтение **запрещено**. Отдельная, проверенная процедура восстановления может завершить переход только после независимой проверки точного совпадения долговечного аутентифицированного файла с pending. Старый файл нельзя автоматически считать допустимым или регистрировать заново.

Два отдельных ресурса не образуют одну атомарную транзакцию. Для восстановления доступности после частичной ошибки потребуется отдельная политика. Специально **не добавлена** операция `CancelPrepare`/сброс authority: она способна сделать откат допустимым.

## Требования и ограничения

- **Независимость:** обычный файл, зашифрованный файл, локальная БД, копия в той же системе резервирования или счётчик в памяти не являются доверенным authority. Нужны защита регистрации и истории от удаления/повторного создания, линейризуемость и подтверждённая устойчивость к аварийному отключению. Реальная реализация ещё не выбрана и не проверена.
- **Первичная регистрация:** исключительно явно доверенная процедура с `Sequence = 1`. Отсутствие authority при открытии существующего хранилища — ошибка. Для миграции существующих данных требуется отдельное подтверждение происхождения.
- **Конкурентность:** необходима согласованная межпроцессная блокировка и запрет устаревшего наблюдения authority. Один CAS не заменяет блокировку файла.
- **Подлинность и гонки:** сравнение хешей не заменяет аутентификацию и проверку UUID, а чтение нельзя отделять от защиты против подмены файла между проверкой и использованием.
- **SA-04 отдельно:** данный контракт не обеспечивает долговечную уникальность AEAD nonce и не реализует `IRollbackProtectedNonceAllocator`.

### Stage 2B1: проверка файла при чтении (эксперимент)

`FileSystemKeyStoreOptions.RollbackAuthority` включает **экспериментальную проверку только при чтении**, но не полноценный защищённый профиль. Требуются `ExpectedStoreInstanceId` и `EnableExperimentalWrites=false`. Каждый `LoadAsync` аутентифицирует файл и сравнивает **те же считанные байты** со свежим состоянием authority под блокировкой; только `CommittedMatch` разрешает вернуть записи. Отсутствие состояния, pending, чужой UUID, откат и ошибка внешнего сервиса приводят к отказу. Автоматического enrollment, prepare, публикации, finalize или recovery нет.

**Нет защиты от downgrade:** вызывающий код может не передать опцию или открыть старый формат v1 старой реализацией. `ProvidesRollbackProtection` остаётся `false` даже с переданной опцией. Функция предназначена только для проверки Stage 1 на настоящем аутентифицированном снимке FileSystem. Для защищённых записей ещё нужны новый outer format/profile pin, долговечный кандидат + intent, CAS с ID запросов, recovery и проверенные барьеры записи на Windows/Linux. Не использовать для production-секретов.


### Этап 2B2: аутентифицированный локальный журнал кандидата (эксперимент, БЕЗ отправки запросов)

Внутренний `RollbackCandidateJournal` создаёт **два отдельных файла без перезаписи** в закреплённом безопасном каталоге хранилища при удержании эксклюзивной межпроцессной блокировки:

- `.rollback-candidate.lsfs`: **точные байты** следующего уже аутентифицированного снимка (без повторной сериализации при восстановлении).
- `.rollback-intent.lsfs`: аутентифицированное корневым протектором намерение с отдельным криптографическим контекстом. Оно связывает UUID хранилища, прежний и следующий глобальные checkpoint, длину снимка и **разные ID запросов prepare/finalize**. Следующий номер строго равен предыдущему + 1.

Сначала записывается, сбрасывается, перепроверяется и публикуется кандидат; затем таким же способом сохраняется намерение. Используются существующие операции, привязанные к дескриптору каталога, и создание без перезаписи. Файлы не удаляются и не заменяются автоматически; неполная пара — ошибка, требующая контролируемого восстановления. Обычная очистка `.pending-*.tmp` не затрагивает эти файлы. При чтении проверяются подпись намерения, аутентификация снимка и точное совпадение отпечатка с checkpoint. Само существование файлов не подтверждает их достоверность.

**Границы этапа:** это отдельный внутренний примитив, проверяемый шестью интеграционными тестами. Включения защищённой записи в обычном API, регистрации authority, `prepare`/`finalize`, разрешения результата через `ResolveAsync`, процедуры восстановления, закрепления профиля и защиты от downgrade **нет**. Старый `IKeyStore` пока не вызывает этот примитив. `ProvidesRollbackProtection=false`, SA-03/SA-04/SA-08 OPEN, Phase 27 NO-GO.

**Предупреждение о долговечности:** Linux после переименования синхронизирует родительский каталог через `fsync`; на Windows сохранность записи каталога после нативного переименования при резком отключении питания **ещё не подтверждена** (гарантии зависят также от файловой системы и оборудования). Успешные тесты журнала не дают разрешения отправлять запросы в реальный authority: сначала нужно проверить устойчивость файла и записей каталога на каждой поддерживаемой платформе. После подключения записи защищённый профиль, неполный журнал, pending на authority и потерянный ответ должны приводить к отказу, а не к незаметному возврату к обычному v1.

### Этап 2B3: чтение и классификация состояния после сбоя (эксперимент)

`RollbackRecoveryInspector` сравнивает **ранее аутентифицированные** кандидат и намерение
из `RollbackCandidateJournal.ReadAsync`, отдельно аутентифицированные байты текущего
снимка, закреплённый UUID и одно свежее линейризуемое состояние authority. Он не
вызывает authority и не меняет файлы. Допустимы только четыре наблюдения:

| Наблюдение | Что увидели |
| --- | --- |
| `StagedWithOldCommitObserved` | Текущий файл и committed совпадают со старым checkpoint; pending отсутствует. Запоздалый prepare всё ещё может выполниться. |
| `PendingWithOldSnapshotObserved` | Pending совпадает с подготовленной следующей версией, а основной файл ещё старый. |
| `PendingWithCandidateObserved` | Pending совпадает с подготовленной версией, основной файл уже содержит её байты. |
| `FinalizedWithCandidateObserved` | Committed и основной файл совпадают со следующей версией, pending отсутствует. |

Все остальные случаи приводят к `Blocked`: authority отсутствует, чужой или
противоречивый, файл изменён, сервер подтвердил новую версию при старом файле либо
новый файл опубликован до подготовки authority. Если старые и новые байты неразличимы,
состояние тоже блокируется. Это **только диагностика**: результат не доказывает
долговечность записи каталога, не разрешает неопределённые запросы prepare/finalize,
повторы, очистку журнала, завершение pending или обычное чтение. Необходимы отдельные
проверки исходов запросов, долговечности, защиты от отключения профиля и аудированный
автомат восстановления. Защищённые записи, RPC и новый публичный API не добавлены.

Добавлены восемь интеграционных тестов Windows/Linux; три включены в обязательный
TRX-контроль. `ProvidesRollbackProtection=false`; SA-03/SA-04/SA-08 открыты, Phase 27 NO-GO.


### Этап 2B4: проверка долговечности при потере питания и запрет преждевременного включения записи (проектное решение, без изменений кода)

**Результат:** защищённая запись пока ЗАПРЕЩЕНА и на Windows, и на Linux. `FileSystemKeyStore` не отправляет изменяющие запросы rollback-authority; `ProvidesRollbackProtection=false`. Этап фиксирует, что именно нужно доказать до включения `prepare`. Новых публичных API, провайдеров и серверов нет.

**Что подтверждено исходным кодом:**

- `RollbackCandidateJournal.WriteNewAsync` создаёт уникальный временный файл под закреплённым каталогом, записывает точные байты, вызывает `FileStream.Flush(true)`, повторно читает и побайтово сравнивает временный файл, затем публикует имя через `LinuxSecureDirectory.Move` либо `WindowsSecureDirectory.Move`.
- На Linux `Move` использует `renameat`/`renameat2` относительно закреплённого каталога и после успешного переименования вызывает `fsync(rootFd)`. Ошибка `fsync` после rename означает **неопределённый результат**, а не право отправлять `prepare`. Это правильная основа, но итоговые гарантии зависят от ФС, параметров монтирования, ядра, накопителя и модели отказа.
- На Windows `Move` делает нативное переименование `NtSetInformationFile(FileRenameInformation)` относительно дескриптора каталога, затем проверяет наличие файла. Наличие файла сейчас и сброс содержимого через `Flush(true)` **не доказывают**, что запись каталога сохранится при отключении питания. Аналог Linux `fsync` для метаданных каталога с подтверждёнными гарантиями в реализации отсутствует.
- На Linux `Remove` выполняет `unlinkat` без последующего `fsync` каталога. До реализации восстановления нельзя полагаться на долговечное удаление журнала: после потери питания старое имя потенциально может вновь появиться. Удаление само по себе не подтверждает завершение восстановления.
- Действующих production-гарантий нет ни для одной платформы. Тесты `Kill`/исключения/перезапуска проверяют логику, **не** сохранность после реального отключения питания.

**Документация платформ:** `fsync(2)` Linux отдельно требует синхронизировать родительский каталог для сохранности имени: https://man7.org/linux/man-pages/man2/fsync.2.html . Windows `FlushFileBuffers` описывает сброс данных файла, но не доказывает сохранность переименования каталога: https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers . У `MOVEFILE_WRITE_THROUGH` явно оговорена гарантия при реализации перемещения через копирование и удаление; подмена текущего нативного переименования на `MoveFileEx` по абсолютному пути без отдельного аудита недопустима: https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw . Сохраняем границу безопасности закреплённых дескрипторов SA-02.

**Обязательное условие будущей записи (ещё не реализовано):** перед отправкой `prepare` точные байты кандидата и аутентифицированное намерение со стабильными ID запросов должны быть записаны с подтверждённой устойчивостью **данных и имён файлов** на поддерживаемой платформе. Аналогичное условие необходимо для публикации активного снимка до `finalize`. Ошибка после rename/барьера — неопределённость: отказ, сохранение материалов восстановления, никакой автоматической перерегистрации или повторной подготовки под новым ID. Тайм-аут authority не означает отказ сервера; для восстановления нужны свежая линейризуемая проверка и подтверждённое разрешение зависшего запроса с блокировкой его позднего исполнения.

**Матрица приёмки с аварийным прерыванием:**

| Место отключения | Требуемое поведение |
| --- | --- |
| Во время записи временного кандидата, до flush | Нет обращения к серверу; частичные данные не выдаются за зафиксированный снимок. |
| После flush файла, до публикации имени кандидата | Нет обращения к серверу; временное имя не считается зафиксированным кандидатом. |
| Во время/после публикации кандидата, до барьера каталога | Неопределённый локальный результат; не обращаться к authority. |
| После кандидата, но до долговечного намерения | Не отправлять `prepare`; неполную пару отклонять и сохранять для диагностики. |
| После долговечных кандидата и намерения, до `prepare` | После перезапуска доступны точные байты и прежние ID запросов; запоздалый RPC нельзя угадывать по обычному чтению. |
| Потеря/задержка ответа `prepare` | Требуется разрешение исходного ID с долговечной блокировкой его позднего исполнения либо отказ. |
| Authority подготовил переход, но активный снимок ещё не опубликован | Обычные чтения запрещены; кандидат сохраняется; восстановление — только по проверенному протоколу. |
| Активный снимок опубликован, но `finalize` ещё не выполнен | Сравнить точные байты, UUID, pending и исходный ID; успех не объявлять. |
| Потеря ответа `finalize` или сбой при удалении журнала | Проверить окончательный исход в authority и активный снимок; повторное появление файлов журнала учитывать консервативно. |
| Сервер подтвердил новую версию, но кандидат исчез/откатился | **Запретить доступ**; без доверенной административной процедуры доступность может быть потеряна окончательно. Никакого отката или скрытой перерегистрации. |

**План испытаний:** полный регрессионный NUnit/CI-прогон, затем отдельный тестовый процесс и изолированная VM с контролируемыми точками прерывания. Принудительное завершение процесса проверяет протокол восстановления, но **не** заменяет жёсткое отключение питания/выключение VM без штатного завершения ОС. Обычная перезагрузка и возврат снапшота VM — разные модели угроз. Для каждого опыта фиксировать версию ОС, ФС, параметры диска/монтирования, гипервизор и кэширование, точку прерывания, checkpoint authority, хеши файлов после запуска и факт отказа в доступе. Повторять с конкурентными процессами. Даже пройденный тест подтверждает только указанную конфигурацию, а не все накопители и контроллеры.

**Решение:** не добавлять лишний `IDurabilityProvider` и не заменять закреплённые операции на потенциально небезопасный path-based `MoveFileEx` ради формальной галочки. Защищённая запись на обеих платформах остаётся выключенной. Дальше — небольшой инструмент испытаний с аварийным завершением и проверка Linux-барьеров/удаления; Windows исследовать отдельно, сохраняя SA-02. Только после этого подключать запись вместе с защитой профиля от downgrade и независимой SA-04 для nonce. SA-03, SA-04, SA-08 — OPEN; Phase 27 — NO-GO.

## Сводная граница интеграции — 21 октября 2026 года

Stage 2B4 выше находился только в копии `design/` приложения; его уникальный анализ сохранён здесь. Прежний путь теперь ссылается на поддерживаемый контракт. Исторический `WriteNewAsync` теперь делегирует `StoreFilePublication`; Linux rename + directory fsync и Windows handle-relative rename сохраняют модель изоляции. Универсальный durability provider и реальный сервер не добавляются.

Read-only inspection теперь отклоняет любое имя rollback-журнала до чтения authority. Старый committed checkpoint не разрешает локально неоднозначный запрос; повреждённые, неполные и полные свидетельства блокируют probe без cleanup. Уже открытый probe проверяет это при каждой загрузке. Это **не** защищённый профиль и не обещание для обычного v1 Open. Диагностический inspector по-прежнему не разрешает мутацию, доступ к материалу, retry или cleanup.

| Операция | Исполняемая поддержка |
| --- | --- |
| Обычные create/write/delete/rotation, root re-protection | Только экспериментальный v1 без rollback-гарантии; ошибка после начала публикации неопределённа |
| Authority inspection, pinned UUID, точные authenticated bytes | Read-only; локальный журнал, pending checkpoint или ошибка authority запрещают доступ |
| Первый enrollment / normal-to-protected migration | BLOCKED; нет автоматической регистрации и fallback при потере сервера |
| Защищённые write/delete/rotation/rekey/re-protection | BLOCKED на Windows/Linux до любого RPC |
| Request-aware согласование prepare/finalize/enroll | Контракты и тестовые модели; production executor отсутствует |
| Восстановление / постоянное удаление журнала / сброс authority | BLOCKED; сохранять свидетельства, проводить доверенное ручное исследование |

Будущий профиль обязан аутентифицировать UUID + authority identity + выбор формата, применять только request-aware fenced mutations, сохранять точный кандидат и исходные authenticated request tuples до отправки, подтверждать долговечную публикацию до finalize и возвращать успех после конечного согласования. Возврат v1 backup до enrollment с обычным/старым Open нельзя защитить одним локальным marker. Нужна независимая доверенная конфигурация; контроль исполняемого кода и всей доверенной конфигурации вне гарантии. Поддерживаемого защищённого профиля нет, пока не решены этот пробел и физические gates. Тесты volatile authority с копированием состояния при рестарте или абстрактным независимым anchor — логическая проверка контракта, а не сертификация провайдера.
