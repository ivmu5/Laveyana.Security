# Laveyana.Security — переносимое восстановление ключей v1 (экспериментально)

[English](PortableKeyRecovery.md) | **Русский**

## Назначение

`PortableKeyRecovery` в `Laveyana.Security.Recovery` защищает **одно экспортируемое значение ключевого материала** для восстановления на другом устройстве. Здесь нет интеграции SQLiteStorage, сети, постоянного хранилища, изменения secret-provider, аккаунтов, паролей или платформенных API. Обычный доступ к секретам уже обеспечивают `SecretHandle` и `ISecretManagementProvider`; ещё один универсальный менеджер жизненного цикла не нужен.

## Формат и гарантии

- Секрет восстановления: **32 криптографически случайных байта** из `GenerateRecoverySecret()` (освобождаемый lease). **Не пароль**: нельзя подставлять пароль аккаунта, короткий PIN или другие низкоэнтропийные значения.
- На каждый вызов `Protect` генерируются новые salt (32 байта) и nonce (12 байт). HKDF-SHA-256 выводит отдельный ключ AES-256-GCM для каждого пакета с версионированным доменом.
- Ограниченный бинарный формат: сигнатура `LKR1`, версия 1, флаги 0, длина исходного материала, salt, nonce, ciphertext и 16-байтный тег аутентификации. Секрет восстановления внутри не хранится.
- AEAD AAD связывает домен, весь заголовок и **внешний неизменный scope** (1–256 байт). Приложение ОБЯЗАНО включать идентичность приложения, назначение, постоянный идентификатор ключа и его версию и восстановить *точно те же байты* на новом устройстве. Scope **не включён** в пакет.
- Один ключ: 1–65 536 байт. `Unprotect` возвращает `SensitiveMaterialLease` только после успешной аутентификации. При ошибке временный буфер расшифрования очищается.
- Ранее правильный пакет можно повторно предъявить: **защиты от rollback и отзыва пакетов нет**. Удаление одной копии не делает недействительными другие.

## Жизненный цикл приложения

1. Для *новых* данных приложение явно создаёт новый ключ. Существующие зашифрованные данные открываются только первоначальным ключом через существующие интерфейсы.
2. **Нельзя** считать `GetAsync == null` на MAUI Android доказательством того, что ключ никогда не существовал. Нельзя автоматически заменять ключ существующих данных. При отсутствии/неопределённости — ошибка или восстановление.
3. Для восстановления приложение экспортирует каждый необходимый ключ и его версию со стабильным точным scope и сохраняет пакеты с **несекретными** метаданными идентичности и формата вместе с согласованной резервной копией данных.
4. Показывать/экспортировать 256-битный секрет восстановления только через доверенный интерфейс или офлайн-канал. **Не** отправлять его на сервер резервных копий, не писать в логи и не хранить рядом с пакетом.
5. При восстановлении сначала проверить пакет и scope, затем безопасно записать ключи в новое защищённое хранилище устройства; при частичной записи или неоднозначном исходе требуется сверка, а не автоматическая перезапись.
6. Допускается экспортировать только действительно экспортируемый материал. Аппаратные неэкспортируемые закрытые ключи таким способом не копируются. Для важных данных нужен отдельный восстанавливаемый ключ данных.

## За пределами реализации и ограничения

- Это **не** резервное копирование всей SQLite, не атомарный пакет множества ключей, не backup manifest, не синхронизация сервером, не KDF для паролей и не универсальный `IKeyStore`.
- Решение **не закрывает** SA-03/04/08, attestation, скрытые ошибки MAUI `SecureStorage` и ограничения истории AES-GCM nonce у software backend. Восстановленные ключи нельзя автоматически импортировать для дальнейшего AES-GCM шифрования с неизвестной историей nonce.
- Потеря секрета восстановления может означать потерю данных. Злоумышленник с пакетом и секретом восстановления сможет его расшифровать.
- Это **новый криптографически чувствительный формат**. Статические проверки и CI unit-тесты **недостаточны** для одобрения хранения ценных ключей реальных пользователей. Впереди независимая криптографическая проверка и платформенная приёмка.
