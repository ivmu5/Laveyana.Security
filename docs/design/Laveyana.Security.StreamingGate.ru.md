# Laveyana.Security — Phase 20 Streaming Security Gate

[English](Laveyana.Security.StreamingGate.md) | **Русский**

## Граница реализации и решение

**Потоковые SHA-256/384/512 и полноразмерные HMAC-SHA-256/384/512 реализованы; сборка и NUnit успешно прошли в Windows/Ubuntu CI 16 октября 2026 года. Потоковое сегментированное AEAD-шифрование ОТЛОЖЕНО / НЕ ПОДДЕРЖИВАЕТСЯ.** Новый формат ciphertext или самостоятельный протокол чанков AES-GCM не вводится. Roadmap позволяет отложить зашифрованную часть Phase 20; полная приёмка этапа не заявляется.

## Гарантии незашифрованного streaming

- `StreamProcessingOptions`: буфер 1..65 536 байт, максимум входа 1 ТиБ, необязательная точная доверенная длина. После достижения лимита проверяется EOF; если данных больше/меньше ожидаемого, чтение завершается ошибкой или произошла отмена, результат не выдаётся.
- Инкрементальный SHA-2 использует `IncrementalHash` и читает данные с текущей позиции до EOF. Сам по себе хеш не подтверждает подлинность.
- HMAC создаёт объект `IncrementalHash` из материала, доступного только через `SensitiveMaterialLease.UseMaterial`. Создание возможно лишь для Active; проверка — по точной Active/Retired версии при наличии capabilities. После чтения сверяется авторитетная ревизия ключа; изменение в процессе вызывает исключение, а не `false`.
- Поток не закрывается и не перематывается. Буфер чтения очищается до возврата в `ArrayPool`. Состояние криптопровайдера освобождается; временные теги очищаются после создания `MacResult`. Внешний интерфейс провайдера не передаёт raw-key bytes.
- Лимит buffer-based AES-GCM (16 МиБ) не меняется; API streaming HMAC не является потоковым AEAD.

## Тесты NUnit (выполнены в H01 CI)

Сравнение всех SHA-2 с эталонным вычислением, пустой и дробный поток, 6 МиБ через буфер 1 КиБ, точные/короткие/лишние байты, отмена, I/O ошибки, запрет SHA-1; HMAC трёх алгоритмов против полного сообщения, неверный tag, ротация/retirement/удаление, запрет capabilities, exact routing, typed key, изменение ревизии при чтении. Golden-ciphertext и AEAD-vectors не заявлены: зашифрованная часть отсутствует.

## Блокирующие требования к AEAD streaming

1. Выбрать проверенную сегментированную AEAD-конструкцию или независимо рецензируемую реализацию, нормативную версию wire-протокола и привязку suite/header.
2. Доказать правила уникальности nonce по версиям, сегментам, процессам, перезапускам и rollback; исключить повтор и непроверенное derivation.
3. Аутентифицировать stream identity, порядок сегментов и **однозначную финальную запись/подтверждение завершения**; не считать поток полностью достоверным до финального подтверждения.
4. Определить ошибки удаления, перестановки, повторения и склейки сегментов, replay, пустого файла и подмены потока.
5. Зафиксировать лимиты, отмену, crash recovery и ошибки; промежуточный plaintext не должен ошибочно считаться полностью аутентифицированным.
6. Получить официальные векторы и межпровайдерную совместимость, отрицательный корпус, fuzzing, отдельный security review, сборку .NET и проверки на разных платформах.

## Открытые ограничения

SDK .NET/NUnit в этом окружении недоступны; выполнение и компиляция кода не подтверждены. Остаются открытыми прежние вопросы FileSystem, rollback protection и Windows TOCTOU. Текущее хранилище не использовать для production-секретов.
