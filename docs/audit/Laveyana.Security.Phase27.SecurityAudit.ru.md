## Объём и метод

Проверены границы семи проектов, исходники провайдеров AES-GCM/HMAC/ECDH/подписи, nonce engine, protected storage, Linux/Windows path guards, Windows DPAPI, sensitive memory, audit и API ввода/вывода, а также имеющиеся тестовые контракты и CI. Выполнены `tools/verify_repository.py` и `tools/verify_documentation.py` с самопроверками. Просмотрены пути исполнения и обработки исключений, повторные обращения к историческим версиям, ограничения размера, копирование входных массивов, очистка секретных буферов. Добавлены тесты мутаций четырёх сериализованных форматов и инъекции ожидания I/O.

**Не выполнялись:** `dotnet restore`, `dotnet build`, NUnit, Windows DPAPI, межпроцессные гонки, тесты с подменой reparse points, реальная аварийная потеря питания, fuzzing работающего C#-декодера. В текущей среде нет .NET SDK. Наличие NUnit-тестов и CI-конфигурации не засчитывается как их успешный запуск.

### Замечания об области применимости

- HPKE `Seal/Open` и streaming AEAD **не поддерживаются**: отсутствие API безопаснее неподтверждённой реализации.
- Secret provider обязан сам выполнять авторизацию; библиотека не объявляет универсальную политику доступа.
- `SensitiveMaterialLease` стирает только собственные managed-буферы; память OS/runtime, копии в callback и удалённые дисковые блоки не охватываются.
- Защита от rollback и nonce uniqueness при нескольких процессах не может быть удостоверена одной локальной статической проверкой.
- Дефектов критичности `CRITICAL` с доказанной эксплуатацией по результатам этого **неполного** review не подтверждено. Это не означает отсутствие таких дефектов.

## Фактически внесённые изменения

1. `SoftwareKeyProviderBackend.Aead.cs`: снимок AAD до первого асинхронного ожидания, ограничение длины **до копирования**, очистка снимка при любом завершении.
2. `ManagedSignatureBackend.cs`: аналогичный снимок входного сообщения до lookup, очистка временного массива при исключении и отмене.
3. `SoftwareAeadEncryptionTests.cs`: два теста на изменение AAD при остановленном metadata lookup.
4. `ManagedMacSignatureTests.cs`: один тест на изменение сообщения в signing/verify при остановленном metadata lookup.
5. `SecurityCodecMutationTests.cs`: детерминированные single-byte mutations и мусорный corpus для `LEP1`, `LDP1`, `LSP1`, `LMR1`; декодирование **не** считается подтверждением аутентичности.

Публичные интерфейсы и сериализованные wire-форматы намеренно не менялись. Два исправления требуют компиляции и проверки совместимости, прежде чем их можно считать принятыми.

## SA-02 — экспериментальное исправление Windows TOCTOU (16 октября 2026 года)

**Раньше:** чтение, временная запись, переименование, блокировка и очистка файлов Windows опирались на строковые пути. ACL и reparse points проверялись отдельно от I/O: между проверкой и операцией путь можно было подменить.

**Что изменено:** новый `WindowsSecureDirectory` удерживает дескриптор корневого каталога и открывает дочерние файлы относительно него с проверками переходов по ссылкам. ACL и владелец проверяются по дескриптору фактически открытого объекта. Переименование и удаление выполняются через дескрипторы, а перечисление временных файлов — через тот же закреплённый каталог. `FileSystemKeyStore` переключён на этот внутренний Windows backend. Поведение Linux, `IKeyStore` и форматы данных не менялись. Добавлены Windows-тесты на символические ссылки и работу с каталогом после переименования его пути.

**Статус: EXPERIMENTAL / TEST ONLY; SA-02 ОТКРЫТА.** На момент подготовки первого кандидата проверок Windows ещё не было; результаты последующей сборки/тестов и исправления переименования приведены ниже. Adversarial-тестирование по-прежнему не выполнено. Она не гарантирует изоляцию от процессов того же пользователя, защиту от rollback и устойчивость к аварийной потере питания. `EnableExperimentalWrites` остаётся обязательным; Phase 27 — **NO-GO** для production и настоящих секретов.

## SA-02 — первый запуск Windows-тестов и исправление переименования (16 октября 2026 года)

Первоначальная экспериментальная реализация собрана в Release под .NET 10, но первый запуск интеграционных тестов на Windows дал **71 тест: 35 пройдено, 22 не пройдено, 14 не выполнялись (платформенные пропуски)**. Все 22 ошибки связаны с `WindowsSecureDirectory.Move`: `SetFileInformationByHandle(FileRenameInfo)` отклонил относительное имя назначения при ненулевом дескрипторе корневого каталога (`ERROR_INVALID_PARAMETER`, Win32 87). Это каскадные сбои инициализации, а не 22 разные уязвимости.

**Кандидат исправления:** переименование временного файла теперь вызывает `NtSetInformationFile(FileRenameInformation = 10)` с проверенным дескриптором исходного файла и уже закреплённым дескриптором каталога назначения. Флаг `ReplaceIfExists` определяет атомарную политику замены. Отката к `File.Move` по имени или Win32-переименованию по абсолютному пути **нет**: это вернуло бы TOCTOU. Ошибки NTSTATUS преобразуются в диагностируемые ошибки Windows. Публичный API и форматы данных не менялись.

**Статус проверки:** исправление подготовлено, но **повторные Windows-тесты ещё не выполнены**. SA-02 остаётся **ОТКРЫТА / EXPERIMENTAL / TEST ONLY**, Phase 27 — **NO-GO**. Нужны повторный Windows integration run, затем adversarial-тесты ACL/junction/race, аварийное восстановление и Linux-регрессии, прежде чем можно будет обсуждать production.

## SA-02 — второй запуск интеграционных тестов Windows (16 октября 2026 года)

После исправления переименования через дескрипторы интеграционные тесты Windows в Release (.NET 10) показали **71 тест: 54 пройдено, 3 не пройдено, 14 не выполнялись**. Прежней общей ошибки переименования `ERROR_INVALID_PARAMETER` (87) в новом прогоне нет.

Все три оставшиеся ошибки возникли **при подготовке тестов**, до вызова проверяемой защиты хранилища. Windows отказала в создании символических ссылок (`File.CreateSymbolicLink` / `Directory.CreateSymbolicLink`) из-за отсутствия привилегии (`ERROR_PRIVILEGE_NOT_HELD`, Win32 1314). Существующие тесты перехватывали `UnauthorizedAccessException`, однако .NET выбросил `IOException`. Затронуты `WindowsSnapshotSymlinkIsRejectedWhenSupported`, `WindowsExistingLockSymlinkIsRejectedWhenSupported` и `WindowsRootDirectorySymlinkIsRejectedWhenSupported`.

**Исправление тестовой обвязки:** пропускать эти проверки *только* при `IOException` с HRESULT `0x80070522` (`HRESULT_FROM_WIN32(1314)`); иные ошибки ввода-вывода должны приводить к провалу теста. Статус `Ignored` **не считается доказательством безопасности**. Для полноценной проверки нужно разрешить создание символических ссылок (например, включить режим разработчика Windows либо использовать среду с соответствующей привилегией) и повторно выполнить все три теста.

**Статус: SA-02 ОТКРЫТА / EXPERIMENTAL / TEST ONLY; Phase 27 — NO-GO.** Проверки символических ссылок в этой среде пока не завершены. Также нужны adversarial-тесты гонок, ACL, junction, аварийного восстановления и регрессии Linux.

## SA-02 — третий запуск Windows: ошибка в обработке отказа lock-файла (16 октября 2026 года)

Универсальный экспортёр тестов Windows/.NET SDK 10.0.402 сообщил **367 тестов: 352 пройдено, 1 не пройден, 14 пропущено по платформенным причинам**. Наиболее существенный прогресс: три Windows-теста на символические ссылки действительно запустились. `WindowsSnapshotSymlinkIsRejectedWhenSupported` и `WindowsRootDirectorySymlinkIsRejectedWhenSupported` прошли. `WindowsExistingLockSymlinkIsRejectedWhenSupported` обнаружил дефект обработки отказа.

**Причина:** `WindowsSecureDirectory.OpenChild` корректно отверг символическую ссылку `.store.lock` с `IOException` («unsafe reparse point or type»), однако `FileSystemKeyStore.AcquireLockAsync` перехватывал **любое** `IOException` в Windows-ветке, повторял вызов до `LockTimeout` (15 с в зафиксированном запуске) и заменял первоначальный отказ на `TimeoutException`. Уязвимая ссылка не открывалась, но настоящий security failure ошибочно выглядел как занятая блокировка и задерживал выполнение.

**Кандидат исправления:** Windows-ожидание и `TimeoutException` допускаются **только** при подтверждённом конфликте совместного доступа (`ERROR_SHARING_VIOLATION`, 32; `ERROR_LOCK_VIOLATION`, 33), полученном через `IOException.HResult` или вложенное `Win32Exception.NativeErrorCode`. Любая другая ошибка ввода-вывода, включая отказ из-за reparse point, немедленно возвращается вызывающему коду с исходным типом и стеком. Linux-ветка, политики тайм-аута при настоящем конфликте, публичный API и формат файлов не изменены. Существующий тест на `.store.lock` регрессирует до исправления и должен проходить после него.

**Статус: исправление подготовлено, повторная сборка и Windows-тесты ещё не выполнены. SA-02 ОТКРЫТА / EXPERIMENTAL / TEST ONLY; Phase 27 — NO-GO.** После устранения этой ошибки необходимы adversarial-тесты подмены файлов/каталогов в гонке, junction/reparse, ACL и Linux-регрессии.

## SA-02 — исправление компиляции конкурентных тестов (16 октября 2026 года)

Первый Windows Release-прогон после добавления двух adversarial-тестов **не дошёл до их выполнения**: `FileSystemKeyStoreTests.cs` не компилируется из-за устаревшего атрибута NUnit `[Timeout]` на строках 829 и 893 (`CS0618`, предупреждения считаются ошибками). Независимые unit-тесты по-прежнему прошли **296/296**. Для интеграционных тестов отчёт TRX не создан.

**Исправление только тестов:** устаревшие атрибуты удалены; в оба теста добавлен локальный `CancellationTokenSource` на 30 секунд. Токен передаётся операциям файлового хранилища и асинхронным задержкам; конкурентные задачи наблюдают отмену и совместно ожидаются до очистки временных каталогов. Ограничение времени кооперативное и не прерывает принудительно синхронные файловые операции.

**Ещё не проверено:** Windows-сборка и выполнение новых тестов после изменения. `SA-02` остаётся **ОТКРЫТОЙ / EXPERIMENTAL / TEST ONLY**; ошибка компиляции не даёт оснований утверждать, что безопасность при гонках подтверждена.

## SA-02 — кандидат проверки Windows junction (16 октября 2026 года)

Последний подтверждённый Windows-прогон Release содержал **369 тестов: 355 пройдено, 0 ошибок, 14 платформенных пропусков** (296 модульных и 59 интеграционных тестов). Проверки обычных символических ссылок и два adversarial-теста прошли. Это подтверждает выполненные сценарии, но не доказывает невозможность всех TOCTOU-гонок.
