# Laveyana.Security — Portable key recovery v1 (experimental)

[Русский](PortableKeyRecovery.ru.md) | **English**

## Purpose

`PortableKeyRecovery` in `Laveyana.Security.Recovery` encrypts **one exportable key-material value** for recovery on another device. No SQLiteStorage dependency, network access, persistent store, secret-provider modification, account service, password entry, or platform API is involved. The existing `SecretHandle` and `ISecretManagementProvider` remain the interfaces for ordinary secret access; no competing general key lifecycle manager is introduced.

## Format and guarantees

- Recovery secret: **32 cryptographically random bytes** generated by `GenerateRecoverySecret()` (disposable lease). **Not a human password**; never substitute account credentials or a low-entropy PIN.
- Every `Protect` call generates a fresh 32-byte salt and 12-byte nonce. HKDF-SHA-256 derives a one-package 256-bit AES-GCM key using a fixed, versioned domain string.
- The bounded binary package contains magic `LKR1`, version 1, reserved flags 0, plaintext length, salt, nonce, ciphertext and a 16-byte authentication tag. It stores no plaintext recovery secret.
- AEAD associated data binds the versioned domain, entire header, and a **caller-provided exact stable scope** (1–256 bytes). Callers MUST include application identity, purpose, persistent key ID and key version, and reproduce precisely the same bytes on recovery. Scope is **not embedded** in the package.
- One plaintext key value: 1–65,536 bytes. `Unprotect` returns a disposable `SensitiveMaterialLease` only after successful authentication. Failed authentication clears the temporary plaintext buffer.
- Copies of previously valid packages may be replayed; there is **no anti-rollback or revocation**. A package can be copied indefinitely. Deleting one backup copy does not invalidate others.

## Application lifecycle

1. For a *new* encrypted dataset, the application explicitly provisions fresh key material. Existing datasets must instead open their original key through the existing provider APIs.
2. **Never** treat `GetAsync == null` on MAUI Android as reliable evidence that a key never existed. Never automatically generate a replacement for an existing encrypted dataset. Missing/uncertain results lead to a recovery/error flow.
3. An application wishing to support recovery exports each needed key material and version with an exact, independently reproduced scope, and stores the encrypted package(s) and necessary **non-secret** identity/format metadata together with a consistent data backup.
4. Display/export the 256-bit recovery secret through an application-controlled trusted UI or offline channel. It must **not** be uploaded to the backup server, logged, or stored next to the encrypted package.
5. On restore, verify the package and scope, then have the application safely provision its new device-owned secret store before enabling access to the restored dataset. A crash, partial write or unclear storage outcome needs explicit reconciliation, not an automatic overwrite.
6. Only key material that is permitted to be exported can be backed up. Hardware-backed non-exportable private keys cannot be recovered this way; use a separate recovery-capable data key.

## Non-goals and security limitations

- **NOT** a backup of a complete database, atomic multi-key bundle, backup manifest, server sync, password-KDF workflow, or generic `IKeyStore`.
- **NOT** a solution to SA-03/04/08, cross-device attestation, Android `SecureStorage` suppressed failures or the software backend's AES-GCM nonce provenance. Restored key material must not be automatically imported for forward AES-GCM encryption where historical nonce use is unknown.
- If recovery secret is lost, recovery may be impossible. If an attacker learns the recovery secret **and** obtains the package, they can decrypt it.
- This portable format is a **new security-sensitive protocol**. Static checks and CI unit tests are necessary but **not sufficient** to approve real users' valuable keys. Independent crypto review and device/platform acceptance remain pending.
