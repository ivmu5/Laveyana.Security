# Laveyana.Security — жизненный цикл ключей приложения (рекомендации по интеграции)

[English](ApplicationSecretLifecycle.md) | **Русский**

## Почему не нужен ещё один менеджер ключей

В Laveyana.Security уже есть `ISecretProvider`, `ISecretManagementProvider`, `SecretHandle` и `PortableKeyRecovery`. Они позволяют **открывать существующий ключ только для чтения** и выполнять **явный переносимый экспорт/восстановление**.

Текущий `ISecretManagementProvider.SetAsync` означает **создать или заменить** по правилам провайдера. Он **не** гарантирует атомарное «создать, только если отсутствует». Последовательность `GetAsync` → `SetAsync` этого не исправляет: два процесса могут соревноваться; на Android скрытый сбой платформенного хранилища может выглядеть как отсутствие ключа. **Нельзя** создавать универсальный `GetOrCreate` для ключей шифрования поверх этого интерфейса.

## Состояния на стороне приложения

| Состояние приложения | Разрешённое действие | Чего нельзя делать |
| --- | --- | --- |
| Заведомо новый пустой набор данных, явная первоначальная настройка | Создать новый ключ в контролируемом приложением процессе и согласовать его с идентичностью данных | Считать `GetAsync == null` доказательством отсутствия данных; перезаписывать существующий ключ |
| Уже существующие зашифрованные данные | `new SecretHandle(reference, provider).UseMaterialAsync(...)`; продолжить, только если callback успешно выполнился | Создавать/подменять ключ при `false` |
| Существующие данные, ключ отсутствует или недоступен | Остановить открытие и предложить отдельный сценарий восстановления | Создавать новый ключ, удалять данные или незаметно сбрасывать состояние |
| Явное восстановление на новом устройстве/в хранилище | Проверить ожидаемый точный scope через `PortableKeyRecovery.Unprotect`; записывать через выбранный приложением безопасный процесс со сверкой исхода | Автоматически перезаписывать действующий ключ; считать ошибку записи или отмену гарантированным откатом |

**Кто определяет, что данные новые?** Само приложение по достоверному состоянию жизненного цикла и происхождению данных, а не по `null` от secret provider. При неоднозначной или частично завершённой инициализации сначала необходимо согласовать состояние. Маркер рядом с ключом, который подвержен тем же сбоям, не является независимым подтверждением.

## Минимальная схема открытия

```csharp
SecretHandle handle = new(secretReference, secretProvider);
bool opened = await handle.UseMaterialAsync(bytes =>
{
    // Использовать заимствованные байты синхронно в разрешённой операции.
    // Нельзя сохранять span или запускать асинхронную работу после callback.
});
if (!opened)
{
    throw new InvalidOperationException(
        "Существующие зашифрованные данные недоступны; требуется явное восстановление.");
}
```

Ошибки провайдера передаются вызывающему коду, их нельзя превращать в признак отсутствия секрета. Успешное чтение ключа ещё не гарантирует правильную идентичность и подлинность данных; проверку должен выполнить сам потребитель. Если аутентификация данных не прошла, нельзя «исправлять» ошибку незаметным созданием нового ключа.

## Ограничения

- `ISecretManagementProvider` не гарантирует атомарный **create-if-absent** или compare-and-swap. Для надёжного параллельного создания требуется соответствующее хранилище/транзакционная граница.
- MAUI `ISecureStorage` не подтверждает независимую долговечность, межпроцессную атомарность и не различает скрытый сбой от настоящего отсутствия.
- `PortableKeyRecovery` защищает только **одно экспортируемое** значение ключа, не согласованную резервную копию множества ключей или данных. Неэкспортируемые аппаратные ключи восстановить таким способом нельзя.
- Восстановление старого AES-GCM ключа не восстанавливает историю его nonce и **не даёт права на дальнейшее шифрование** через software backend (SA-04).
- Это схема интеграции и демонстрационные тесты, **не** допуск к защите ценных production-ключей. Ограничения SA-03/04/08 и отсутствие тестов на физических устройствах сохраняются.

NUnit-сценарии `ApplicationSecretLifecycleTests` демонстрируют открытие, скрытую потерю с `null` и явное восстановление через существующие публичные API. Они не моделируют атомарное постоянное хранение и не доказывают безопасность реального платформенного backend.
